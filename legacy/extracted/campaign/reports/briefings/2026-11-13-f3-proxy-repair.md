# Прокси восстановлен для SDK/CLI-воркеров

**Сбой подтвердился: мой новый CLI-запуск не включал HTTP-транспорт Pi, учитывающий прокси. Сам настроенный прокси работал.** Исправленный процесс уже получает ответы модели и выполняет ревью F3. Проверка физического соединения показывает настроенный прокси и ноль неожиданных внешних соединений. Общий математический мост этим отчётом не принимается.

Предыдущий вывод, что совпадающие HTTP_PROXY/HTTPS_PROXY исключают ошибку проксирования, был неверен. Переменные окружения не доказывают фактический маршрут. Вывод о необходимом внешнем исправлении регионального доступа был преждевременным.

## Точная причина

Обычный Pi инициализирует `configureHttpDispatcher()`. Официальный @piewf/cli создаёт SDK-сервисы напрямую и этот bootstrap не выполняет. Более того, импорт SDK загружает npm Undici8.10.2: при отсутствии его dispatcher API2 создаётся обычный Agent, который записывается также в совместимый глобальный dispatcher API1. Поэтому даже Node `--use-env-proxy`, включённый ранее, после импорта SDK оказался недостаточен.

Это воспроизведено локально на том же стеке OpenAI/CLI SDK, а не выведено только по ответу403. Источники: CLI initialization, SDK `core/http-dispatcher.js`, Undici `lib/global.js`. Пути и итоги собраны в `artifacts/workflow-recovery/f3-proxy/diagnosis.json`.

## Что проверено машиной

Команда:

```
python3 -B artifacts/workflow-recovery/f3-proxy/test_sdk_proxy_v2.py
```

Пять случаев на локальных origin/proxy, без внешних запросов и реальных ключей:

| Конфигурация | Соединений с proxy | Запросов к origin | Результат |
|---|---:|---:|---|
| Только proxy env | 0 | 1 | Обнаружен прямой маршрут |
| Native Node flag, до импорта CLI | 1 | 1 | Прокси используется |
| Native flag, затем импорт CLI | 0 | 1 | Воспроизведён сброс dispatcher |
| Импорт CLI, затем штатный Pi dispatcher | 1 | 1 | Прокси используется |
| То же, но proxy отказывает | 1 | 0 | Ошибка, прямого fallback нет |

Все проверки прошли; `maxRetries=0`. Свидетельство: `transport-regression-v2.json` и новые v2 raw streams. Более ранний тест без импорта полного CLI тоже сохранён: он был корректен в своём объёме, но недостаточно представлял реальный запуск.

Отдельный запрос без ключа и без генерации через уже настроенный proxy получил HTTP401. Наблюдалось только соединение с настроенным proxy. Это проверка маршрута/связности, не проверка авторизации модели. Фактический рабочий запрос после исправления уже получил ответы: running-агент имеет ненулевую usage/вывод модели вместо прежнего403.

## Исправление

- `scripts/piewf-proxied-entry-v2.mjs` загружает CLI SDK, затем вызывает его собственный `configureHttpDispatcher()` перед `runCli`.
- `--use-env-proxy` наследуется Node-дочерними процессами через task-local NODE_OPTIONS; существующие настройки сохраняются.
- `scripts/require-proxied-node-v2.mjs` проверяет заданный proxy для provider destinations и сохраняет только обезличенные счётчики физических соединений. Неожиданное внешнее соединение останавливает задачу, а не считается допустимым direct fallback. Это процессная диагностика/защита, не OS firewall.
- Этот модуль импортируется обычным кодом доверенного host-wrapper, а не через наследуемый `--import`: иначе он попадал в ограниченный workflow-child и ломал его старт. Первоначальный такой сбой сохранён; sandbox permissions не ослаблялись. Исправленный canary с реальными evidence/shell завершился exit0.
- Запуск контролирует `scripts/run-f3-proxied-host-v3.py`, disk reserve600 MiB и ограниченное время жизни. Это не цикл повторов запросов провайдеру.

Ни proxy URL, ни ключи, ни endpoint, ни глобальные конфиги/пакеты не менялись. Речь о восстановлении использования уже заданного прокси. Установленный CLI отдельно резолвит SDK package с version1.0.0, тогда как основной Pi release1.5.2; этот version mismatch отмечен, но не исправлялся попутным обновлением.

Рабочий запуск: `60a29210-822e-4f49-b795-f19f56604557`, `aro-ogu-to-aro-formal-v3-proxied-v3`. Подтверждены running и реальные ответы модели. Root snapshot: 11 инструментов, 0 MCP; у агента read/bash/edit/write/workflow_result. Прежние модели, математические цели и контрольные барьеры сохранены.

Текущие сведения: `artifacts/workflow-recovery/f3-proxy/proxied-host-v3/`, включая transport, start.json и capability-check.json. Пассивный monitor `b09575d2-e8c3-43d7-bd06-720e859056a9` только доставляет итог; математических агентов не запускает. Доказательный host живёт отдельно от этого notifier.

Сохранены все предыдущие ошибки: исходный MCP-resume;403 без инициализации; bootstrap failure от наследуемого диагностического import;403 после одного лишь native flag. Они не объявлены успешными задним числом. Все изменения запусков были явными и мотивированы новыми проверками, без смены провайдера/модели и без автоматического provider retry loop.

F1/F2 сохраняют проверенные доказательства. F3 сейчас проходит прежнюю цепочку statement review → proof → independent replay. F4 и unrestricted-policy correspondence остаются незавершёнными. Коммитов/пушей, живых научных записей или аттестации не было.
