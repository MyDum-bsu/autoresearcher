## 1. Назначение

Движок ведёт долгий поиск новых математических результатов в области двустадийной
ARO (fixed recourse, FME+Dual, мост к оптимальному гарантированному управлению):
генерирует гипотезы, атакует их контрпримерами, доказывает выживших, улучшает
алгоритмы на бенчмарках — и ведёт живую карту доказанного (blueprint), из которой
агент-писатель собирает черновики глав. Человек — редактор, рулевой и единственная
научная власть: аттестует узлы, распределяет бюджет поиска, правит текст.
Поверх всего — оценщик: телеметрия, скоринг компонент, алерты.

## 2. Архитектура: пять контуров

```
              ┌───────────────────────────────────────────────────────┐
              │  ЧЕЛОВЕК: сессии ревью · аттестации · редактура текста │
              └──────▲──────────────────────────────▲─────────────────┘
                     │ диффы, досье, алерты         │ черновики
   ┌────────────┐  ┌─┴────────────┐  ┌─────────────┴──────┐
   │ ПАМЯТЬ      │◄─┤ ПОИСК        ├─►│ ТЕКСТ              │
   │ blueprint   │  │ эволюционный │  │ scribe: главы только│
   │ DAG узлов   │  │ цикл + роли  │  │ из закрытых узлов   │
   └─────▲──────┘  └─┬────────────┘  └────────────▲───────┘
         │           │ выборка/мутации            │ anchor-lint
         │      ┌────▼──────────────┐             │
         └──────┤ СУДЬИ (код, не    ├─────────────┘
      статусы   │ LLM): численные,  │  доказательство
                │ символьные, Lean  │
                └───────────────────┘
   ┌────────────────────────────────────────────────────────────────┐
   │ ОЦЕНЩИК: телеметрия всех контуров · скоркарды компонент · алерты│
   │ ИНТЕРФЕЙСЫ: CLI (запись) + веб-дашборд (наблюдение)             │
   └────────────────────────────────────────────────────────────────┘
```

- **Память** (Тао/blueprint): DAG узлов — единственный стор научной истины.
- **Поиск** (FunSearch/AlphaEvolve): цикл популяция → судья → отбор → мутация.
- **Судьи** (FunSearch/AlphaProof): детерминированный код + Lean; LLM к судейству
  не допускается. Именно это делает допустимым одного провайдера.
- **Текст** (AI Scientist): сборка и компиляция, с жёсткими линтерами.
- **Оценщик** (собственная разработка): наблюдает за первыми четырьмя, не участвуя.
- **Дисциплина** (ZIB): уровни автономии, бюджетированные циклы, обязательные
  сессии человека, дискрепанс-протоколы.

## 3. Память: blueprint-DAG

- Формат: YAML-файл(ы) + генератор, рендерящий граф зависимостей и статус-таблицу.
  С первого дня нотация совместима с leanblueprint (`\lean`, `\leanok`).
- Узел: `{id, kind: definition|conjecture|lemma|theorem|example|experiment|counterexample,
  statement (LaTeX), deps, evidence[], origin: seed|run:<id>|human, status}`.
- Статусы (конвейер + две терминали):
  `seed → conjectured → survived-falsifier → numerical → dual-verified → formalized → attested`
  и терминали `refuted`, `descoped(причина)`. Численный PASS ≠ символьная истина;
  статусы — оси, не градиент одного «VERIFIED».
- Стартовое содержимое: только seed-вопросы из исходной структуры работы
  (5–7 шт., RQ-уровень), явно помеченные `origin: seed` — это идея, не утверждение.
  Никакого ингеста литературы или легаси-claims.
- Инвариант одного стора: всё научное состояние — в blueprint + артефакты прогонов
  на диске + append-only журнал событий (§13). Трекер задач — только ручные записи
  человека; раннер его не трогает и ничего не создаёт сам.

## 4. Материалы: политика доверия

- **Единственный перенос из старого проекта** — исходная литература (PDF/TeX) и
  структура работы как идея. Обработка/структурирование литературы — заново.
- Манифест `corpus/MANIFEST.md`: путь + sha256 + дата; добавление — отдельным
  действием человека. Формулы/теоремы/числа — только прямым чтением PDF
  (layout-чувствительное, с координатами), TeX — построчно.
- **Anchor-first, не batch-ingest**: факт извлекается из PDF только когда циклу
  он нужен; попадает в blueprint как citation-узел с file+page. Обзорные карты
  строятся как кэш по мере надобности, никогда как основание утверждения.
- Старый репозиторий — замороженный архив: консультации возможны, цитирование —
  никогда; всё оттуда помечается `origin: legacy-archaeology` и статуса не получает.

## 5. Судьи: детерминированный код (три типа)

1. **Judge-Numerical** (алгоритм-трек): семейства инстансов (генераторы с seed),
   метрики = gap к известным границам / время; сетки и эталоны замораживаются ДО
   прогонов; held-out семейства против подгонки; регресс против бейзлайнов.
   Точных рациональностей — где возможно (Julia `Rational`, HiGHS/точные LP).
2. **Judge-Symbolic** (теорем-трек): sympy/SageMath — проверка алгебраических
   шагов (элиминации, двойственные переходы, перестановки кванторов); согласие
   primal/dual как обязательный инвариант.
3. **Judge-Formal** (ядро): Lean 4 + mathlib; компиляция `lake build` = 0 ошибок —
   единственный путь статуса `formalized`. Правило допуска в текст диссертации:
   центральная теорема входит в главу только с `\leanok`.

Плюс сквозной **двойной маршрут** для дериваций: символьный маршрут и
численно-точный маршрут обязаны сойтись; расхождение = falsify-событие.
LLM не судит никогда — она генерирует, атакует текстово и пишет.

## 6. Поиск: эволюционный цикл и треки

Трек A — **алгоритмы** (дёшев, быстр): популяция конструкций (выбор направлений/
сценариев, процедуры проекций, декомпозиции) → Judge-Numerical → отбор →
LLM-мутации (островная модель: ниши по идеям, квоты разнообразия против
вырождения). Бюджет: тысячи дешёвых локальных оценок, сотни LLM-вызовов.

Трек B — **теоремы и оценки** (adversary-first): Explorer выдвигает формулировку →
statement-lint → Adversary ищет контрпример (adversarial LP, перебор сеток,
граничные случаи) → выжившая проходит двойной маршрут → кандидат в Lean-ядро,
если несущая. Опровержение — перв-class результат, фиксируется в DAG как
counterexample-узел.

Трек C — **мост ОГУ↔ARO** (полуручной): перенос конструкций из A2–A5 в ARO;
машинная часть — проверка соответствия на полигональных инстансах; смысловая —
человек. Самая уникальная ниша, самый высокий удельный вес человека.

Дискрепанс-протокол (урок M2): расхождение с внешним числом → ≤2 автоматных
попытки объяснить → досье (что пробовано, что исключено) → человек + внешний
ground truth (полные таблицы PDF, errata, письмо авторам). Гринд запрещён бюджетом.

## 7. Роли агентов

Все роли — один провайдер; различие — контракт и скилы, не модель.

| Роль | Делает | Пишет | Запрещено |
|---|---|---|---|
| orchestrator | бюджетирует циклы, stop-conditions, собирает диффы к сессии | лог цикла | менять статусы узлов |
| archivist | anchor-first чтение PDF по запросу цикла, ведение манифеста | citation-узлы, кэш-обзоры | формулы из .md-конверсий |
| explorer | генерация гипотез/конструкций/мутаций | candidate-узлы `conjectured` | доказывать, подтверждать, повышать статусы |
| adversary | поиск контрпримеров, граничных случаев, атака формулировок; steelmanning своих же позиций (паттерн pravo-ritorika) | counterexample-узлы, досье расхождений | «подтверждать» |
| deriver | двойные маршруты вывода; Lean-попытки (ассистент) | proof-artifacts, lean-файлы | судить свой вывод (судья — код) |
| scribe | черновики глав из закрытых узлов, сборка/компиляция LaTeX | `thesis/draft/*.tex` | новые утверждения без узла; менять математику |
| оценщик | см. §10 — наблюдает, считает, алертит; науку не трогает | телеметрия, scorecards | автоматически отключать компоненты (кроме пробития бюджета) |
| человек | аттестации, бюджет, направление, редактура текста | decisions-легер | — (единственная научная власть) |

Разделение интересов: author_run ≠ judge_result всегда — судья это код;
два LLM-продукта (генерация и её проверка текстом) не образуют верификации.

### 8.1 Внешние глобальные скиллы (уже установлены, EN/RU)

| Скилл | Что делает | Этапы применения |
|---|---|---|
| **`logika`** (v2.1, классическая логика по Челпанову): проверка и починка аргументов — силлогизмы, определения, деления понятий, индукция, аналогии; поиск паралогизмов | deriver (скетч доказательства до сдачи судьям), adversary (логические дыры формулировок), scribe (аргументация черновика), человек (редактура) |
| **`technical-style-editor`** (v0.3): прямой доказательный стиль, анти-канцелярит и анти-«машинный текст»; есть детерминированный скрипт `lint_technical_style.py --language ru` | scribe (каждый черновик), финальная редактура глав, README/отчёты/досье |

### 8.2 Паттерн тривиума (перенос из pravo-серии)

Юридический цикл «грамматика → логика → риторика» переносится как обязательный
конвейер над любым математическим текстом — в этом смысле «правильность понимания
написанного» проверяется трижды, на разных плоскостях:

1. **Форма однозначна** (`statement-lint`, доменный чекер): сколько прочтений
   допускает формулировка; область действия кванторов и отрицаний — прямой аналог
   синтаксической неоднозначности из pravo-grammatika.
2. **Вывод валиден** (`logika`): следует ли заключение из посылок; определения и
   деления не меняют объёма; нет подмены тезиса.
3. **Изложение ясно** (`technical-style-editor`): без канцелярита и нейрослопа.

Два дисциплинарных правила той же серии становятся правилами конвейера:
- **«Не выдумывай дефект»** — сдержанность при ревью: замечание только с указанием
  конкретного места и типа ошибки;
- **«По памяти не подставляй — ставь флаг [требует проверки]»** — у нас: любая
  внешняя опора = PDF-якорь file+page или гейт-артефакт, никогда цитата по памяти.

## 9. Формат работы

**Цикл (такт)** — бюджетированный запуск: выбор фронт-узлов → explorer/adversary/
deriver по контрактам → судьи (код) → обновление DAG → инкрементальный черновик.
Бюджеты: LLM-вызовы/токены, wall-clock, локальный compute; всё логируется в журнал.
Длинные циклы — в песочнице (Docker), т.к. код из поиска перестаёт быть доверенным.

**Сессия человека** (ритм ~неделя, ZIB-принцип «ревью — часть процесса»):
дифф статусов DAG; досье дискренсов; скоркарды и алерты оценщика; распределение
бюджета; аттестации; редактура черновиков. Сессия — единственное место научных
решений и единственное место правки порогов алертов.

**Уровни автономии** (ZIB): старт Level 3 (человек запускает каждый цикл);
Level 4 (агент крутит циклы между сессиями) — только для exploration-зон и только
после метрик фазы 1. Autonomy — отчётная величина, не оптимизируемая цель.

## 10. Оценщик: мониторинг эффективности компонент и метрики

Наблюдает за всеми контурами, не участвуя в науке. Всё считается кодом из журнала
событий — ручных таблиц нет, LLM-оценки эффективности нет (Гудхарт).

**Телеметрия** (структурированные события пишутся каждым компонентом автоматически):
- цикл: длительность, бюджет LLM, decisive/indecisive (изменился ли статус узла);
- судья: время, детерминизм (повторный прогон → тот же вердикт), дискриминативность
  (доля отклонённых кандидатов: 0% и 100% — оба подозрительны);
- скил/чекер: срабатывания, ложные срабатывания (отменено человеком), латентность;
- роль: стоимость на продвинутый узел, доля брака по стадиям;
- Lean: выгорание таймбокса, число соскальзываний;
- инфраструктура: сбои, повторные запуски, recovery-события.

**Скоркарды компонент** (скользящее окно): `вклад / стоимость`, где вклад машинно
считаем (продвинутые узлы, пойманные дефекты, отклонённые плохие кандидаты),
стоимость = токены + wall-clock. Провальный скоринг не отключает компонент
автоматически (кроме жёсткого пробития бюджета) — он попадает в досье сессии.

**Алерты** (пороги фиксируются в конфиге на фазу; правка — только человеком в сессии):
- жёсткие (немедленное уведомление): crash-loop, пробитие бюджета цикла,
  недетерминизм судьи, потеря воспроизводимости артефактов;
- мягкие (в досье сессии): cost/узел растёт 3 цикла подряд; adversary ничего не
  убивает N циклов (гейты ослабли — прямой урок старого проекта); scribe требует
  >K правок на страницу; доля впустую-циклов >50%; Lean-таймбокс на 80% без прогресса.

**Метрики научные (главные):** узлы по ярусам (formalized/dual-verified/numerical/
refuted) во времени; покрытие ядра (\leanok/ядро); бенчмарк-дельта на held-out;
число опровержений (считается, квот НЕТ); якорный охват черновиков = 100%.
**Метрики процессные (отчётные):** вмешательств/цикл; доля decisive-циклов; MTTR
дискренсов; LLM-стоимость/цикл; wall-clock/цикл.

## 11. Интерфейсы: CLI — запись, веб-дашборд — наблюдение

- **CLI (`ro`) — единственный интерфейс записи**: все операции (запуск цикла,
  судья, аттестация, конфиг алертов, экспорт) работают headless, детерминированно,
  пригодны для cron/CI. Всё, что меняет состояние, проходит через CLI и журнал.
- **Локальный веб-дашборд — поверхность наблюдения** (read-only к журналу и DAG):
  - карта blueprint: интерактивный DAG, статусы цветом; клик по узлу → полная
    родословная (кто предложил, какие атаки, прогоны судей, кто аттестовал);
  - «тропа идеи»: цепочка seed→…→attested/refuted;
  - таймлайн циклов и лента событий: принято/отвергнуто/дескопедано, причина строкой;
  - скоркарды компонент и лента алертов оценщика;
  - просмотрщик PDF-якорей (переход к странице источника);
  - диффы к сессии человека.
  Только localhost, без внешних сетей; безопасность — CSRF/path-traversal/секреты
  (верный инстинкт старого rpm.7.5 сохраняем).
- **TUI — опционально позже** (`ro top`: живой статус цикла в терминале).
- **GUI/desktop — нет**: ничего не даёт поверх браузера, усложняет сборку.

## 12. Прогресс и результаты: всё видимо, ничего не стирается

- **Append-only журнал событий** (JSONL): каждый переход статуса, вердикт судьи,
  решение человека — с hash артефактов. Единственный источник для дашборда,
  диффов, метрик и скоркардов; удаление и правка записей невозможны в принципе.
- **Отвергнутое — первоклассный результат**: refuted-узлы и провалившиеся кандидаты
  хранятся вечно — с контрпримером и причиной; «пантеон опровержений» — отдельный
  вид дашборда (M2-урок: опровержение ценнее тихого совпадения).
- Запросы из CLI: `ro log --since <date>`, `ro nodes --status=refuted`,
  `ro trail <node>` — родословная любого результата.
- Прогресс-вид: burn-up узлов по ярусам во времени (наука без фиксированного
  бэклога — burn-down невозможен и вреден) + карта покрытия seed-вопросов.
- Дайджест к каждой сессии: принятое/отвергнутое/дескопеданное, алерты, дифф DAG,
  ожидаемые решения человека.

## 13. Фазы и критерии переходов

**Фаза 0 — Фундамент (недели 1–4).** Новый репозиторий; манифест литературы;
blueprint-скелет с seed-вопросами; генераторы инстансов и замороженные сетки;
скилы v1 (доменные чекеры + подключение `logika`/`technical-style-editor`);
append-only журнал; CLI; Lean-проект компилируется; один сквозной микро-цикл на
игрушечном ARO-инстансе (explore → attack → judge → DAG → абзац черновика);
CI-воспроизводимость.
*Выход:* микро-цикл детерминированно воспроизводим (2 прогона → идентичные
артефакты); каждое изменение статуса ловится журналом; anchor-lint ловит
подставленную ошибку; рендер blueprint работает.

**Фаза 1 — Поисковый цикл (месяцы 2–3).** Трек A полностью; adversary на треке B;
scribe с черновиками; дискрепанс-протокол; **оценщик v1** (телеметрия + жёсткие
алерты + скоркарды) и **дашборд v1** (карта DAG + таймлайн + лента событий).
*Выход:* ≥10 циклов без вмешательства внутри цикла; ≥1 конструкция устойчиво бьёт
бейзлайн на held-out; ≥3 зафиксированных опровержения; cost/цикл плоский; скоркарды
считаются без ручного ввода; черновик главы 1 компилируется с нулём неякорных
предложений.

**Фаза 2 — Теоремный трек и формальное ядро (месяцы 4–8).** Dual-route конвейер;
выбор 2–3 теорем ядра ИЗ ВЫЖИВШИХ (не предзаказанных); Lean-формализация с
таймбоксом (при исчерпании — `descoped(причина)`, алерт оценщика на 80% таймбокса);
трек C: мостовые узлы с машинно-проверяемыми инстансами.
*Выход:* ядро \leanok или дескопед с явной причиной; треки связаны в DAG;
held-out улучшения трека A удерживаются; ≥1 мостовой результат аттестован.

**Фаза 3 — Автономия и сборка (месяцы 9–12+).** Level-4 зоны для exploration;
полные черновики глав; редактура автора; защитный пакет: диссертация + карта
blueprint (что чем доказано) + перепрогоняемый воспроизводимости-пакет.
*Выход:* текст к защите собран ИЗ ФАКТИЧЕСКИ ВЫЖИВШИХ узлов — расхождение с
исходным замыслом оформляется как находка, а не как провал.

## 14. Что сознательно НЕ строим (уроки критики)

- Batch-ингест литературы/легаси в граф — никогда (anchor-first).
- Два стора истины и автосоздание задач раннером — никогда.
- Autonomy как целевая метрика; квоты на фальсификации; ручные таблицы метрик;
  LLM-оценка эффективности компонент — никогда (только код из журнала).
- Same-model «свежий процесс» как несущая верификация — только двойные маршруты.
- Гринд на дискренсах — бюджет 2 попытки, затем досье и человек.
- PEPit — навсегда (чужой домен). Writer, изобретающий математику, — никогда.
- Автоотключение компонент оценщиком — никогда (кроме пробития бюджета).
- Доказательство «перепроверить весь легаси» — долг не создаём: не используем и всё.

## 15. Риски и ответы

| Риск | Ответ |
|---|---|
| Подгонка под бенчмарк | held-out семейства, замороженные сетки, смена сетки = отдельное решение человека |
| Вырождение популяции (одна модель) | острова/ниши, квоты разнообразия, судья — код (давление отбора модель-независимо) |
| Застревание в Lean | ядро выбирается из выживших; таймбоксы + алерт на 80%; `descoped` — честный исход |
| Лоскутный мат-текст scribe | тривиум-конвейер (statement-lint → logika → style) на каждом черновике; финальная редактура человека |
| Уход от защитимой диссертации | ежесессийная сверка «карта DAG ↔ требуемый вклад»; seed-вопросы как якорь |
| Полное расхождение с исходным замыслом | принято автором заранее; оформляется как результат поиска |
| Стоимость LLM | тяжёлое локально; LLM — только генерация/чтение/текст; бюджеты на цикл; алерты оценщика |
| Оценщик сам становится багом | пороги только в конфиге; правка только человеком в сессии; сам оценщик метрик не «улучшает» |
